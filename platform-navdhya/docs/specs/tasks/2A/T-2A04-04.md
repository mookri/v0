## Objective

Store credit is a double-entry-style ledger: `store_credit_accounts` cache a balance that MUST equal the sum of the append-only `store_credit_ledger`. Staff issue (sensitive, ACR 2), checkout consumes in the order transaction with a unique ledger ref (= order id, so no double spend under concurrency), refunds can route back to credit, and expiry posts `expire` lines as a batch.

## Scope

**In scope:**

- `store_credit_accounts` + append-only `store_credit_ledger` (issue/consume/refund/adjust/expire kinds, optional expiry per issue)
- Issue/adjust staff endpoints (sensitive, ACR 2) + return-flow credit resolution
- Checkout consumption as a payment method captured in the order transaction
- Balance invariant test (cached balance = ledger sum) + expiry batch

**Out of scope:**

- Credit purchase (buy-now-pay-later) — different mechanism — owned by Deferred
- Cash-out of credit — owned by Out of scope v1

## Acceptance criteria

1. **AC-T-2A04-04-1** — Invariant holds: `store_credit_accounts.balance` equals Σ `store_credit_ledger` signed amounts at all times — enforced by a property test that runs random issue/consume/refund/expire sequences.
2. **AC-T-2A04-04-2** — Checkout consumption posts the ledger row in the same transaction as the order with ref = order id (UQ): a concurrent duplicate consume attempt fails without double spend.
3. **AC-T-2A04-04-3** — Issue and adjust require the sensitive permissions with ACR 2 step-up; every ledger row carries a ref and kind, and manual adjustments are audited.
4. **AC-T-2A04-04-4** — Events `customer_accounts.credit.issued` / `.consumed` / `.refunded` / `.adjusted` / `.expired` are emitted with account + ref identifiers (amounts in payload per the event register).
5. **AC-T-2A04-04-5** — GIVEN a principal lacking `customer_accounts:store_credit:issue` / `customer_accounts:store_credit:adjust` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
6. **AC-T-2A04-04-6** — Tenant isolation holds: every new table (`store_credit_accounts`, `store_credit_ledger`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
7. **AC-T-2A04-04-7** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
