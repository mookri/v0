## Objective

Staff can create draft orders that are projections over the single sales-order aggregate: a `draft_orders` record wraps an underlying `sales_orders` row in status `draft`, carries a hashed invoice-link token with validity, and completes into a normal order when the buyer pays through the invoice link. Draft numbering follows the `DO-<yyyy>-<seq>` scheme; order_ops owns draft metadata only — never stock or cash.

## Scope

**In scope:**

- `draft_orders` entity + state machine (`open|invoice_sent|completed|cancelled`)
- Invoice link generation (hashed token, `valid_until`) + buyer completion flow through checkout capture
- Draft → order completion transition; draft numbering via the invoicing numbering-scheme pattern
- Draft order API under `/api/v1/order-ops/drafts`

**Out of scope:**

- Post-placement order editing — owned by [T-2A02-02](./T-2A02-02.md)
- Deposits & payment terms on drafts (the schedule machinery) — owned by [T-2A02-04](./T-2A02-04.md)

## Acceptance criteria

1. **AC-T-2A02-01-1** — A draft order wraps exactly one underlying `sales_orders` row in status `draft` (UQ `sales_order_id`); completing the draft transitions the underlying order forward — no second order aggregate is created (ADR-0006 projection rule).
2. **AC-T-2A02-01-2** — `POST /order-ops/drafts/{id}:send-invoice` stores the hashed token, sets status `invoice_sent`, and the buyer completion endpoint converts the draft to a paid/authorized order; an expired or unknown token returns 410 with envelope code `draft_link_expired`.
3. **AC-T-2A02-01-3** — Events `order_ops.draft.created` / `.invoice_sent` / `.completed` / `.cancelled` are emitted with draft + underlying order references and correlation ids.
4. **AC-T-2A02-01-4** — Draft order numbers follow `DO-<yyyy>-<seq>` allocated through the numbering-scheme mechanism; allocation is atomic per tenant.
5. **AC-T-2A02-01-5** — GIVEN a principal lacking `order_ops:draft:view` / `order_ops:draft:create` / `order_ops:draft:update` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
6. **AC-T-2A02-01-6** — Tenant isolation holds: every new table (`draft_orders`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
7. **AC-T-2A02-01-7** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
