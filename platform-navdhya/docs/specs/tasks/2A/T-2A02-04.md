## Objective

Orders support split payment: deposit/installment schedules where each entry captures through the payments contract with its own idempotency key, and B2B payment terms (net-N) where checkout creates the order with `payment_status=on_terms` and an AR invoice issued immediately with the term's due date — collection flowing through AR, never gateway capture. The order's payment status reflects the schedule aggregate.

## Scope

**In scope:**

- `payment_schedules` (deposit/installment/balance) with per-entry capture + status
- Schedule capture via payments contract (per-entry idempotency keys); `payments.payment.captured` advances entries
- Payment-terms checkout path: `on_terms` status + immediate AR invoice with due date
- Terms eligibility sourced from B2B-lite attributes (E-2A-14)

**Out of scope:**

- Dunning of overdue term invoices — owned by [T-4A11-04](../4A/T-4A11-04.md)
- Deposit refund mechanics — owned by Phase 1 payments baseline

## Acceptance criteria

1. **AC-T-2A02-04-1** — GIVEN a 30/70 deposit schedule WHEN the deposit capture succeeds THEN the schedule entry moves to `captured`, `order_ops.deposit.captured` is emitted, and the order's `payment_status` reflects the schedule aggregate (partial).
2. **AC-T-2A02-04-2** — Each schedule entry captures with its own idempotency key: replaying a capture request for an entry returns the stored result without a second charge.
3. **AC-T-2A02-04-3** — GIVEN a buyer with an eligible payment term WHEN checkout completes THEN the order is created with `payment_status=on_terms`, an AR invoice is issued immediately with the term's due date, and no gateway capture is attempted.
4. **AC-T-2A02-04-4** — Events `order_ops.deposit.captured` / `.schedule_completed` and `order_ops.terms.invoice_issued` are emitted with order + schedule/invoice references.
5. **AC-T-2A02-04-5** — GIVEN a principal lacking `order_ops:schedule:view` / `order_ops:schedule:capture` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
6. **AC-T-2A02-04-6** — Tenant isolation holds: every new table (`payment_schedules`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
7. **AC-T-2A02-04-7** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
