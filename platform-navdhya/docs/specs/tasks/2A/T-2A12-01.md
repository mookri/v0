## Objective

Gateway drivers declare what they can do: `payment_accounts.gateway_config` gains a parsed `capabilities` block (cards, wallets[], refunds full|partial, captures manual|auto, stored_instruments, webhooks) maintained by the driver on configuration and refresh. Checkout renders wallet options strictly from declared capabilities — a wallet never appears unless the gateway declares it — and capability changes propagate to checkout rendering without redeployment.

## Scope

**In scope:**

- Parsed `capabilities` block schema + driver maintenance hooks (configure/refresh)
- Checkout wallet-option rendering driven exclusively by declared capabilities
- Capability validation on gateway config saves; refresh propagation

**Out of scope:**

- New gateway integrations — owned by Phase 1 payments baseline
- Stored-instrument tokenization flows (capability flag only) — owned by Phase 1 payments baseline

## Acceptance criteria

1. **AC-T-2A12-01-1** — Checkout renders wallet options strictly from declared capabilities: GIVEN a gateway config without `apple_pay` in `capabilities.wallets` WHEN checkout lists payment options THEN Apple Pay is absent from the response — undeclared wallets are never selectable.
2. **AC-T-2A12-01-2** — The capabilities block validates on gateway config save: malformed shapes (non-enum refunds/captures values, non-array wallets) reject with named validation codes; the driver refreshes the block on configuration changes.
3. **AC-T-2A12-01-3** — Capability changes propagate without redeployment: updating a gateway's capabilities changes the next checkout payment-options response (no cached stale options beyond the documented cache window).
4. **AC-T-2A12-01-4** — The capabilities block is additive on `payment_accounts.gateway_config`: existing gateway configs without the block behave as cards-only (conservative default), asserted by regression fixtures.
5. **AC-T-2A12-01-5** — GIVEN a principal lacking `payments:account:configure` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
6. **AC-T-2A12-01-6** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
