## Objective

Confirmed and partially fulfilled orders can be edited through the only sanctioned post-confirmation mutation path: propose an edit (add/remove/modify lines, shipping, discount) with a restock flag, validate prices and stock, then apply idempotently — reserving for adds, releasing reservations and optionally restocking fulfilled quantities, recomputing totals, and emitting a full before/after delta. Raw status/totals writes remain prohibited.

## Scope

**In scope:**

- `order_edits` + `order_edit_lines` append-only edit ledger
- Edit validation (price re-resolution, `StockAvailability` for adds, `totals_delta` computation)
- Idempotent `:apply` (sensitive above amount threshold) with restock movement + optional refund + credit note
- Edit rejection with no side effects

**Out of scope:**

- Editing cancelled/closed orders — immutable by design
- Refund policy decisions (payments module owns refund mechanics) — owned by Phase 1 payments baseline

## Acceptance criteria

1. **AC-T-2A02-02-1** — GIVEN a confirmed order WHEN an edit adding a line is applied THEN stock is reserved for the new line via the inventory reservation path and `sales_orders.totals` reflects the recomputed totals in the same transaction.
2. **AC-T-2A02-02-2** — GIVEN a fulfilled line removed with `restock=true` WHEN the edit is applied THEN a restock movement is created, the reservation is released, and refund + credit note are initiated through the payments/invoicing contracts per the edit's flags.
3. **AC-T-2A02-02-3** — `POST /order-edits/{id}:apply` is idempotent: replaying the apply returns the stored result without duplicate movements, refunds, or events.
4. **AC-T-2A02-02-4** — Event `order_ops.edit.applied` carries the full before/after delta (lines, shipping, discounts, totals); `.proposed` and `.rejected` carry the edit reference without side effects.
5. **AC-T-2A02-02-5** — Edits are append-only: no UPDATE touches `order_edits` rows after creation; rejected edits remain readable with status `rejected`.
6. **AC-T-2A02-02-6** — GIVEN a principal lacking `order_ops:edit:view` / `order_ops:edit:create` / `order_ops:edit:apply` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-2A02-02-7** — Tenant isolation holds: every new table (`order_edits`, `order_edit_lines`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-2A02-02-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
