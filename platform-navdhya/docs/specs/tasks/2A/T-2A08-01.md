## Objective

Discount rules gain one additive condition key — `applies_on_sale_items` (default `true`) stored in the rule's conditions JSON with no schema migration. When `false`, the rule does not apply to lines already reduced by another rule or a manual discount (lines carrying `discount_applications`). The evaluation algorithm is unchanged otherwise; eligibility filtering consults the flag per line.

## Scope

**In scope:**

- Condition key support in `promotion_rules.conditions` (additive JSON, default true)
- Eligibility filtering in evaluation steps 3/4 consulting the flag per line
- Rule configuration surface exposing the flag with default semantics
- Golden-fixture stack tests (rule stacking, manual discount interaction)

**Out of scope:**

- New evaluation algorithm semantics beyond the one flag — owned by By design
- Per-discount stacking groups — owned by Deferred post-v1

## Acceptance criteria

1. **AC-T-2A08-01-1** — GIVEN a rule with `applies_on_sale_items=false` and a cart line already reduced by another rule or manual discount WHEN discounts evaluate THEN the rule skips that line while applying to unaffected lines in the same cart.
2. **AC-T-2A08-01-2** — Legacy rules without the key behave as `applies_on_sale_items=true` (default) — no behavior change for existing rules (regression fixture asserted).
3. **AC-T-2A08-01-3** — The flag is stored in the rule's conditions JSON: no schema migration ships with this task, and the conditions schema validation accepts the key with boolean values only.
4. **AC-T-2A08-01-4** — Rule configuration endpoints expose the flag; evaluation responses attribute per-line application so the skip is observable in the discount-applications output.
5. **AC-T-2A08-01-5** — GIVEN a principal lacking `discounts:rule:view` / `discounts:rule:create` / `discounts:rule:update` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
6. **AC-T-2A08-01-6** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
