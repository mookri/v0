## Objective

One barcode resolution contract serves every scan workflow: `BarcodeLookup.resolve(code, tenant)` matches barcode then SKU on products/variants (indexed, tenant-isolated, null on miss), powering admin/POS scan lookup, receive-by-scan on GRN lines, pick-by-scan confirmation with mismatch rejection, and POS sell-by-scan with offline idempotency. No parallel per-channel lookup logic may exist.

## Scope

**In scope:**

- `Catalog\Contracts\BarcodeLookup` contract + kernel implementation (exact barcode → exact SKU → null)
- `GET /api/v1/catalog/barcodes/{code}` scan lookup (variant summary + availability via inventory contract)
- Receive-by-scan (GRN line entry accepts barcode), pick-by-scan (mismatch ⇒ 422 `inventory_pick_mismatch`, no silent substitution)
- POS sell-by-scan cart adds with offline local_seq idempotency

**Out of scope:**

- Barcode generation/printing — owned by Deferred post-v1
- Alias/synonym barcode tables — owned by Deferred seam

## Acceptance criteria

1. **AC-T-2A06-01-1** — Resolution order holds: exact barcode match wins over SKU; no match returns null mapped to 404 `catalog_barcode_unknown`; resolution never crosses tenant boundaries (cross-tenant barcode returns not-found, asserted).
2. **AC-T-2A06-01-2** — Pick-by-scan mismatch rejects: GIVEN a pick line for variant A WHEN the scanned code resolves to variant B THEN the request returns 422 `inventory_pick_mismatch` with no substitution or partial confirmation.
3. **AC-T-2A06-01-3** — `GET /api/v1/catalog/barcodes/{code}` returns the variant summary + availability snapshot for holders of `catalog:product:view` and 403 otherwise.
4. **AC-T-2A06-01-4** — POS offline scans queue with local_seq idempotency: replaying a synced scan batch produces no duplicate cart lines (idempotency test on the sync endpoint).
5. **AC-T-2A06-01-5** — GIVEN a principal lacking `catalog:product:view` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
6. **AC-T-2A06-01-6** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
