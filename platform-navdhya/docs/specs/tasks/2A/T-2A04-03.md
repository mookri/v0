## Objective

Buyers maintain named wishlists: `wishlists` + `wishlist_items` (variant, position, added_at) per buyer profile, with add/remove/reorder operations and a move-to-cart flow that re-validates availability.

## Scope

**In scope:**

- Wishlist entities promoted to normative (per the domain register)
- CRUD + position management under the buyer surface; move-to-cart with availability re-check

**Out of scope:**

- Shared/public wishlists — owned by Deferred post-v1
- Wishlist-based notifications — owned by Deferred post-v1

## Acceptance criteria

1. **AC-T-2A04-03-1** — Wishlist items are unique per (wishlist, variant); position updates are atomic and list order is stable under concurrent updates (feature test).
2. **AC-T-2A04-03-2** — Move-to-cart re-validates availability: unavailable variants stay in the wishlist and are reported, available ones move into the cart.
3. **AC-T-2A04-03-3** — Wishlist endpoints are buyer-scoped: a buyer can read/modify only their own wishlists (403 otherwise).
4. **AC-T-2A04-03-4** — GIVEN a principal lacking `customer_accounts:profile:view` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
5. **AC-T-2A04-03-5** — Tenant isolation holds: every new table (`wishlists`, `wishlist_items`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
6. **AC-T-2A04-03-6** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
