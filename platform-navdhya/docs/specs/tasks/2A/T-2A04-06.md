## Objective

Customer records carry staff notes and tags in the customers module (admin surface): notes with author membership and audit trail, tags mirrored for filtering and segmentation inputs — complementing the order-level annotations of T-2A02-03.

## Scope

**In scope:**

- Customer notes + tags entities in the customers module (admin-owned)
- CRUD endpoints on the customers surface; audit on every write
- Tag mirror consistency for customer filtering

**Out of scope:**

- Buyer-visible notes (internal staff data only) — owned by By design
- Tag-driven automation — owned by Deferred post-v1

## Acceptance criteria

1. **AC-T-2A04-06-1** — Customer notes are staff-internal: no buyer-facing surface renders them (response-shape test across buyer endpoints).
2. **AC-T-2A04-06-2** — Tag writes mirror consistently for filtering; every note/tag mutation writes an audit record with actor + customer reference.
3. **AC-T-2A04-06-3** — Note/tag endpoints enforce `customers:customer:view|update` permissions; cross-tenant customer references return 403/404 fail-closed.
4. **AC-T-2A04-06-4** — GIVEN a principal lacking `customers:customer:view` / `customers:customer:update` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
5. **AC-T-2A04-06-5** — Tenant isolation holds: every new table (`customer_notes`, `customer_tags`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
6. **AC-T-2A04-06-6** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
