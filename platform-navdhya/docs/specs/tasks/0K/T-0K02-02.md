## Objective

Working Context — the current operating node — is resolved server-side into a concrete `(hierarchy_id, node_id, scope_mode)` for every authorized request, and the hard invariant `WorkingContext ⊆ MaximumAuthority` is enforced: client-supplied context can narrow but never expand authority. Forged-context requests are denied, named, and logged as a dedicated test class; multi-hierarchy resolution is deterministic and hierarchy structure edits are versioned.

## Scope

## Acceptance criteria

1. **AC-T-0K02-02-1** — Working Context resolves server-side for every authorized request in HIER-007 order: explicit request node, else persisted context, else the principal's default authority root; the resolved triple is recorded on the execution context.
2. **AC-T-0K02-02-2** — Invariant `WorkingContext ⊆ MaximumAuthority` holds: GIVEN a requested context node outside the principal's maximum authority WHEN the request is issued THEN the platform returns 403 with envelope code `forged_context_denied` and writes a full denial log entry (forged-context denial test class, HIER-011).
3. **AC-T-0K02-02-3** — Multi-hierarchy principals resolve contexts independently per hierarchy type; a request touching two hierarchies resolves both deterministically with no cross-hierarchy bleed (HIER-012).
4. **AC-T-0K02-02-4** — GIVEN a hierarchy node that is deactivated or moved outside the principal's authority WHEN a persisted context references it THEN subsequent requests fail closed into re-resolution — context is never silently widened or served stale (HIER-013/014).
5. **AC-T-0K02-02-5** — Hierarchy structure edits bump a structure version; context resolutions record the version they were computed against and stale resolutions are re-derived on the next request.
6. **AC-T-0K02-02-6** — GIVEN a principal lacking `platform:context:resolve` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-0K02-02-7** — Tenant isolation holds: every new table (`working_contexts`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-0K02-02-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
