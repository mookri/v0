## Objective

The kernel owns typed hierarchies: seven built-in types (`organization`, `management`, `sales_territory`, `warehouse`, `legal_entity`, `project`, `custom`), node/relationship CRUD with cycle prevention, and authority roots binding principals to nodes with scope modes (`SELF|NODE|DIRECT_CHILDREN|SUBTREE`). This is the structural prerequisite for Working Context and for all parity surfaces that scope data by hierarchy position.

## Scope

**In scope:**

- Hierarchy/node/relationship/authority-grant schema + CRUD endpoints
- Built-in type seeding at provisioning; custom type declaration via manifest
- Cycle prevention + atomic subtree reparenting; authority grant resolution per scope mode

**Out of scope:**

- Working Context resolution and the ⊆ invariant — owned by [T-0K02-02](./T-0K02-02.md)
- Context switching UX and org-tree migration — owned by [T-0K02-03](./T-0K02-03.md)

## Acceptance criteria

1. **AC-T-0K02-01-1** — The seven built-in hierarchy types are seeded per tenant at provisioning (idempotent re-seed is a no-op); custom types can be declared via module manifests and appear in `module:list` output.
2. **AC-T-0K02-01-2** — Node/relationship CRUD endpoints under `/api/v1/hierarchies` enforce parent→child edges within a single hierarchy and reject cycle-creating edges with envelope code `hierarchy_cycle_forbidden`.
3. **AC-T-0K02-01-3** — An authority grant binding a principal to a node with scope mode `SUBTREE` resolves to exactly that node's descendant set (asserted against fixture trees); `SELF`, `NODE`, and `DIRECT_CHILDREN` resolve per HIER-005 semantics.
4. **AC-T-0K02-01-4** — Reparenting a node moves its entire subtree atomically, writes an audit record, and preserves authority grants (grants follow nodes, not positions).
5. **AC-T-0K02-01-5** — GIVEN a principal lacking `platform:hierarchy:configure` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
6. **AC-T-0K02-01-6** — Tenant isolation holds: every new table (`hierarchies`, `hierarchy_nodes`, `hierarchy_relationships`, `authority_grants`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
7. **AC-T-0K02-01-7** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
