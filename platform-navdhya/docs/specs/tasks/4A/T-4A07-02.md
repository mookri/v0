## Objective

Batch masters (`stock_batches`: batch_number UQ per tenant+variant+supplier, expiry_on, received_ref, status) become authoritative: batch-tracked variants carry batch on every movement, and `stock_levels` gains `batch_id` in its unique key (additive migration → `(tenant_id, variant_id, location_id, batch_id)`). Reservation allocates earliest-expiry batches first for variants flagged FEFO (per-variant allocation strategy `fifo|fefo`); expired batches are excluded from sellable allocation. The `TraceQuery` contract resolves genealogy upstream (which GRNs/supplier batches fed a batch) and downstream (which orders/work orders consumed it) from movement refs — powering recall workflows. A daily expiry job marks batches `expired` past `expiry_on` and emits `inventory.batch.expired` (feeds notifications + quality).

## Scope

**In scope:**

- `stock_batches` (variant_id, batch_number UQ per tenant+variant+supplier, expiry_on NULL, received_ref, status) + additive `stock_levels.batch_id` in the unique key → `(tenant_id, variant_id, location_id, batch_id)`
- Batch-tracked variants carry batch on every movement (GRN batch/expiry fields become authoritative)
- FEFO allocation: per-variant allocation strategy flag (`fifo|fefo`); FEFO variants reserve earliest-expiry batches first; expired batches excluded from sellable allocation + surfaced in a batch-expiry report
- `TraceQuery` contract: upstream (GRN/supplier-batch origins) + downstream (order/work-order consumers) resolution from movement refs — recall workflows
- Daily expiry job: marks batches `expired` past `expiry_on`, emits `inventory.batch.expired` (feeds notifications + quality)

**Out of scope:**

- Full WMS lot-directed put-away — owned by Deferred post-v1
- Batch-level costing (valuation stays method-driven per variant, T-4A07-03) — owned by By design

## Acceptance criteria

1. **AC-T-4A07-02-1** — FEFO ordering holds: GIVEN batches B1 (expiry 2026-09-01), B2 (expiry 2026-10-01) for an FEFO-flagged variant WHEN a reservation for 10 units allocates THEN B1 is consumed before B2 (allocation ledger asserted); a `fifo`-flagged variant allocates by receipt order instead (both strategies feature-tested).
2. **AC-T-4A07-02-2** — Expired-batch exclusion: GIVEN a batch past `expiry_on` WHEN sellable allocation runs THEN the batch is never allocated; the daily expiry job marks it `expired`, emits `inventory.batch.expired`, and the batch surfaces in the expiry report — job replay is idempotent (no duplicate events).
3. **AC-T-4A07-02-3** — Genealogy correctness: GIVEN fixture movements (GRN → transfer → order issue + work-order consumption) WHEN `TraceQuery` resolves a batch THEN upstream returns the originating GRN/supplier batch and downstream returns every consuming order/work order (fixture-asserted); cross-tenant genealogy returns nothing (contract test).
4. **AC-T-4A07-02-4** — The `stock_levels` unique key rebuild is additive + backfilled: existing level rows gain `batch_id NULL` and the new UQ `(tenant_id, variant_id, location_id, batch_id)` holds — batch-tracked movements without a batch reject with a named error; non-batch variants are unaffected (regression).
5. **AC-T-4A07-02-5** — Movement events for batch-tracked variants carry additive batch refs; `inventory.batch.expired` carries batch + variant refs (no amounts); the expiry job's event fan-out feeds notifications + quality without synchronous coupling (listener tests).
6. **AC-T-4A07-02-6** — GIVEN a principal lacking `inventory:stock:view` / `inventory:transfer:create` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A07-02-7** — Tenant isolation holds: every new table (`stock_batches`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A07-02-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
