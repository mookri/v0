## Objective

Checklist process automation layered on the employee aggregate: reusable `hr_checklist_templates` (ordered items with role + due offset) are auto-instantiated by lifecycle events — `hr.employee.activated` spawns onboarding, `hr.employee.terminated` spawns offboarding — idempotent per (employee, kind, trigger event). Items are workflow-managed tasks with computed due dates, overdue surfacing, and skip-with-note; completion of all items completes the instance. Checklist items MUST NOT contain personal data (titles are role-action descriptions only), and employees see/complete their own items through the existing `/me/hr/*` self-service surface.

## Scope

**In scope:**

- `hr_checklist_templates` (code UQ per tenant, kind `onboarding|offboarding`, items JSON ordered [{title, role, due_offset_days}], status) + `hr_checklist_instances` (template_code, employee_id, kind, status `in_progress|completed|cancelled`, one active instance per employee per kind) + `hr_checklist_items` (instance_id, title, assigned_role `hr|it|manager|employee`, due_on, status `pending|done|skipped`, completed_by, completed_at, notes)
- Event-driven instantiation: `hr.employee.activated` → active onboarding template; `hr.employee.terminated` → offboarding template; idempotent per (employee, kind, trigger event)
- Item lifecycle: `due_on` = trigger date + `due_offset_days`; overdue items surface in the HR queue + emit `hr.checklist.item_overdue` (debounced daily); skip requires a note and the assigned role's permission
- Completion: all items `done|skipped` ⇒ instance `completed` → `hr.checklist.completed`
- Self-service: `GET /me/hr/checklist` + `POST /me/hr/checklist/items/{id}:complete` for `employee`-role items
- PII ban: checklist item titles are role-action descriptions only — no personal data (HR sensitivity class)

**Out of scope:**

- Recruitment/ATS, performance management, scheduling, loans — owned by Deferred (planning DF-14…DF-17)
- Free-form checklist creation outside templates — owned by By design — templates are the only source

## Acceptance criteria

1. **AC-T-4A04-01-1** — Instantiation idempotency holds: GIVEN an `hr.employee.activated` event WHEN the same event is redelivered (outbox retry) THEN exactly one active onboarding instance exists for the (employee, kind, trigger event) tuple — asserted by replay test against the unique constraint.
2. **AC-T-4A04-01-2** — Item lifecycle correctness: items receive `due_on` = trigger date + `due_offset_days`; overdue items emit `hr.checklist.item_overdue` at most once per day (debounce test); skip requires a note and the assigned role's permission (skip by a non-assigned-role actor rejects).
3. **AC-T-4A04-01-3** — Completion rollup: WHEN all items of an instance reach `done|skipped` THEN the instance transitions to `completed` with `completed_at` set and `hr.checklist.completed` emitted; an instance with any `pending` item never completes.
4. **AC-T-4A04-01-4** — PII ban enforced: a feature/schema test asserts checklist item titles validate against the personal-data pattern rules (role-action descriptions only), and template configure is flagged sensitive (step-up) because template edits affect live processes.
5. **AC-T-4A04-01-5** — Self-service surface: `GET /me/hr/checklist` returns only the caller's own items; `POST /me/hr/checklist/items/{id}:complete` succeeds only for items assigned to the `employee` role belonging to the caller (cross-employee completion rejects with 403/404).
6. **AC-T-4A04-01-6** — Events `hr.checklist.instantiated`, `hr.checklist.item_completed`, `hr.checklist.item_overdue`, `hr.checklist.completed` are emitted with instance/item refs — payloads carry no personal data beyond membership ids (payload-schema test).
7. **AC-T-4A04-01-7** — GIVEN a principal lacking `hr:checklist:view` / `hr:checklist:configure` / `hr:checklist:item_update` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
8. **AC-T-4A04-01-8** — Tenant isolation holds: every new table (`hr_checklist_templates`, `hr_checklist_instances`, `hr_checklist_items`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
9. **AC-T-4A04-01-9** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
