## Objective

Opportunities progress through per-pipeline workflow state machines: `crm_pipelines` + ordered `crm_stages` (probability defaults, declarative entry actions executed as workflow hooks), terminal `won`/`lost` states with guards (won requires customer_id, lost requires lost_reason), audited reopen of lost opportunities, and won-events feeding the forecasting module.

## Scope

**In scope:**

- `crm_opportunities` (number `OPP-<seq>`, amount, probability, expected close, status open|won|lost) + `crm_pipelines` + `crm_stages`
- Per-pipeline workflow state machine with transition guards; stage entry actions (create activity task, notify owner, set probability) as workflow hooks with rollback on failure
- Pipeline/stage configuration surface (`crm:pipeline:configure`, sensitive)
- Won/lost/reopen flows with mandatory reason on lost + reopen

**Out of scope:**

- Activities + campaigns — owned by [T-4A01-03](./T-4A01-03.md)
- Customer 360 rollups — owned by [T-4A01-04](./T-4A01-04.md)
- Forecasting models (intelligence consumes won events) — owned by P6 roadmap

## Acceptance criteria

1. **AC-T-4A01-02-1** — Stage transitions are workflow-guarded: GIVEN an opportunity in stage S WHEN moved to stage T THEN the transition passes through the workflow engine with `crm:opportunity:update`, entry actions run as hooks, and a failing hook rolls back the transition (no half-applied stage change).
2. **AC-T-4A01-02-2** — Terminal guards hold: `won` requires `customer_id` set (422 otherwise) and emits `crm.opportunity.won`; `lost` requires `lost_reason`; reopening a lost opportunity requires a mandatory reason, is audited, and emits `crm.opportunity.reopened`.
3. **AC-T-4A01-02-3** — Events `crm.opportunity.created` / `.stage_changed` / `.won` / `.lost` / `.reopened` are emitted with opportunity + stage references; `.won` payloads are the forecasting module's input (schema stability contract with intelligence).
4. **AC-T-4A01-02-4** — Stages are ordered per pipeline by `position`; pipeline configuration (add/reorder stages) requires `crm:pipeline:configure` (sensitive) and reordering never strands in-flight opportunities (stage ids remain valid).
5. **AC-T-4A01-02-5** — GIVEN a principal lacking `crm:opportunity:view` / `crm:opportunity:create` / `crm:opportunity:update` / `crm:pipeline:configure` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
6. **AC-T-4A01-02-6** — Tenant isolation holds: every new table (`crm_opportunities`, `crm_pipelines`, `crm_stages`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
7. **AC-T-4A01-02-7** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
