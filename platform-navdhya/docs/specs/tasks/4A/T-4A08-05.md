## Objective

TDS is applied at payout: payout batches consult `supplier_tds_profiles` (supplier-level section + rate config); applicable payouts compute TDS, reduce the paid amount, and post the deducted amount to a TDS-payable account via posting rules; the supplier receives a TDS certificate artifact (kernel Files) per period. TCS applies on sales where applicable (e.g. e-commerce): checkout/invoice adds TCS via the tax engine as an additive computed component (the engine stays jurisdiction-generic), posted to TCS-payable. Events carry refs, section, and rate — amounts stay out of events.

## Scope

**In scope:**

- `supplier_tds_profiles` (supplier_id, TDS section, rate, status; tenant-scoped) — supplier-level TDS rule config
- TDS at payout: payout batches consult profiles; applicable payouts compute TDS, reduce the paid amount, and post the deducted amount to the TDS-payable account via posting rules
- TDS certificate artifacts per supplier per period (kernel Files); export under `india_statutory:certificate:export`
- TCS on sales (where applicable): checkout/invoice adds TCS via the tax engine as an additive computed component; posted to TCS-payable
- Events `india_statutory.tds.deducted` (payment ref, section, rate — amounts stay out of events), `india_statutory.tcs.collected`

**Out of scope:**

- TDS return filing (26Q etc.) — owned by Deferred post-v1 — certificates + postings are the v1 surface
- TCS return filing — owned by Deferred post-v1
- Jurisdiction logic inside the tax engine — TCS rides the additive-component extension, not engine branches — owned by By design (ADR-0008)

## Acceptance criteria

1. **AC-T-4A08-05-1** — TDS at payout: GIVEN a supplier with a TDS profile (section + rate) WHEN a payout batch executes THEN the paid amount is reduced by the computed TDS, the deducted amount posts to the TDS-payable account via posting rules (balanced), and the supplier's net payout matches the computation; suppliers without profiles pay out gross (both paths feature-tested).
2. **AC-T-4A08-05-2** — Certificate artifacts: per supplier per period, a TDS certificate artifact generates via kernel Files with deduction details; export requires `india_statutory:certificate:export` and is audited; certificate content matches the posted deductions for the period (reconciliation test).
3. **AC-T-4A08-05-3** — TCS via tax engine: GIVEN a taxable sale where TCS applies WHEN the invoice computes taxes THEN TCS appears as an additive tax-engine component (engine code unchanged — architecture test asserts no India-specific branches) and posts to TCS-payable via posting rules.
4. **AC-T-4A08-05-4** — `supplier_tds_profiles` validates: section + rate required, UQ per (tenant, supplier, section), status machine gates applicability; profile configure requires `india_statutory:tds:configure` with step-up (sensitive) and is audited (rate changes never rewrite already-deducted payouts).
5. **AC-T-4A08-05-5** — Events `india_statutory.tds.deducted` (payment ref, section, rate — no amounts) and `india_statutory.tcs.collected` (invoice ref, rate — no amounts) are emitted; payload-schema tests assert amounts never appear.
6. **AC-T-4A08-05-6** — GIVEN a principal lacking `india_statutory:tds:view` / `india_statutory:tds:configure` / `india_statutory:certificate:export` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A08-05-7** — Tenant isolation holds: every new table (`supplier_tds_profiles`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A08-05-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
