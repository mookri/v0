## Objective

Customer 360 is an eventual read model built purely from events: refresh listeners consume `customers.*`, `sales.order.*`, `service.ticket.*`, `crm.opportunity.*`, `crm.activity.logged`, and contract reads (`ReceivablesAging` from AR), debounced to at most once per 60 s per customer and idempotent. The API exposes staleness (`stale: true` beyond 15 min), the listener's query surface is architecture-tested against cross-module joins, and opportunity-won events provide the forecasting module's CRM input.

## Scope

**In scope:**

- `crm_customer_360_views` read model (orders/opportunities/tickets/credit summaries, last_activity_at, refreshed_at)
- Refresh listeners on the registered event set; debounce + idempotency; staleness exposure
- Read endpoint guarded by BOTH `crm:insight:view` AND `customers:customer:view`
- Stable `crm.opportunity.won` payload contract as the forecasting input (ERP-007 delta)

**Out of scope:**

- Forecasting models/pipelines (intelligence module consumes the events) — owned by P6 roadmap
- Real-time (sub-debounce) freshness — owned by By design

## Acceptance criteria

1. **AC-T-4A01-04-1** — The read model is event-built with no cross-module joins: the architecture test asserts the listener's query surface, and a fixture event stream converges to the expected summaries (reconciliation test).
2. **AC-T-4A01-04-2** — Refresh is debounced (max once per 60 s per customer) and idempotent: replaying the same event batch yields identical rows; `refreshed_at` advances once, and the API returns `stale: true` when the model is older than 15 minutes.
3. **AC-T-4A01-04-3** — The 360 endpoint requires BOTH `crm:insight:view` and `customers:customer:view` — holding only one returns 403 (dual-guard asserted).
4. **AC-T-4A01-04-4** — `crm.customer_360.refreshed` is emitted after each refresh; `crm.opportunity.won` payloads carry the stable schema (amount, pipeline, stage, campaign refs) that the forecasting module consumes — schema pinned in the event catalog.
5. **AC-T-4A01-04-5** — GIVEN a principal lacking `crm:insight:view` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
6. **AC-T-4A01-04-6** — Tenant isolation holds: every new table (`crm_customer_360_views`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
7. **AC-T-4A01-04-7** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
