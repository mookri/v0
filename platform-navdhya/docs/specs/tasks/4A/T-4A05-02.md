## Objective

Approved expense reports complete the money path: `expense_reimbursements` route payouts through the payments module's payout batch flow (SoD applies; `payments.payout.executed` marks the report `reimbursed`), billable lines become project-billing inputs via the published `ExpenseBillableQuery` contract (projects consumes `expenses.report.approved`), and `expenses.report.reimbursed` posts via posting rules (debit category account, credit payout/bank; billable amounts to receivable-suspense until re-invoiced). Travel context rides on the report's `trip_ref` (purpose + date range) for travel-claim reporting.

## Scope

**In scope:**

- `expense_reimbursements` (report_id, payout_ref → payments, amount Money, status `pending|paid|failed`, paid_at)
- `POST /reports/{id}:reimburse` (`expenses:reimbursement:execute`, sensitive) → payments payout batch (`payments.payout.*` flow); `payments.payout.executed` marks the report `reimbursed`
- Billable re-charge: lines with `billable=true` + customer_id feed the projects billing run via the `ExpenseBillableQuery` contract published here (projects consumes `expenses.report.approved`)
- GL posting on `expenses.report.reimbursed`: debit expense category account (via `gl_account_key`), credit payout/bank account; billable amounts post to receivable-suspense until re-invoiced
- Travel context: `trip_ref` JSON (purpose, from/to dates) on reports — travel-claim filtering + reporting

**Out of scope:**

- Expense report capture/approval mechanics — owned by [T-4A05-01](./T-4A05-01.md)
- Project billing run itself (projects module consumes the contract) — owned by Projects baseline
- Multi-currency reimbursement FX handling beyond report currency — owned by By design

## Acceptance criteria

1. **AC-T-4A05-02-1** — Reimbursement routes through payments: `POST /reports/{id}:reimburse` creates an `expense_reimbursements` row (`pending`) and enqueues a payments payout batch; `payments.payout.executed` transitions the reimbursement to `paid` and the report to `reimbursed`; payout failure lands in `failed` with the failure surfaced (no silent loss).
2. **AC-T-4A05-02-2** — SoD on payout: the reimbursement execution honors payments payout SoD (the executor cannot be the sole approver of the underlying report's approval chain where tenant policy requires dual control) — asserted via the payments payout SoD tests.
3. **AC-T-4A05-02-3** — Billable uniqueness: a line with `billable=true` + customer_id appears in exactly one project billing run — the `ExpenseBillableQuery` contract exposes consumed markers, and double-consumption by the projects billing run rejects (contract + feature test).
4. **AC-T-4A05-02-4** — GL posting balance: `expenses.report.reimbursed` posts debit = Σ category accounts (via `gl_account_key`) and credit = payout/bank account; billable amounts post to the receivable-suspense account until re-invoiced — postings are balanced and consume the posting engine (no direct ledger writes).
5. **AC-T-4A05-02-5** — Events `expenses.report.reimbursed` (report + reimbursement refs) drive posting; travel reports carry `trip_ref` and are filterable by trip date range on read endpoints (feature test).
6. **AC-T-4A05-02-6** — GIVEN a principal lacking `expenses:reimbursement:execute` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A05-02-7** — Tenant isolation holds: every new table (`expense_reimbursements`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A05-02-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
