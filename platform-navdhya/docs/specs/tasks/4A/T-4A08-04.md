## Objective

GST return exports as report definitions following the finance_reports pattern: GSTR-1 (outward supplies from issued invoices + debit/credit notes) and GSTR-3B (summary tax liability + ITC from inward registers). Export files follow the portal schema (JSON/CSV) pinned per adapter version; generation is queued and produces a reconciliation summary (invoice count vs export count, tax totals) so omissions are diagnosable before upload. ITC reconciliation against portal 2A/2B feeds is deferred — the export surface is the v1 commitment.

## Scope

**In scope:**

- Report definitions (finance_reports pattern): GSTR-1 (outward supplies from issued invoices + debit/credit notes) and GSTR-3B (summary tax liability + ITC from inward registers)
- Export files in portal schema (JSON/CSV) pinned per adapter version; emitted version recorded on each artifact
- Queued generation with reconciliation summary: invoice count vs export count + tax totals (diagnosable before upload)
- Events `india_statutory.return.generated` / `.failed` (report refs + reconciliation summary, no per-invoice amounts)

**Out of scope:**

- ITC reconciliation against portal 2A/2B feeds — owned by Deferred (planning DF-24)
- Portal upload automation — owned by Out-of-platform in v1
- IRN registration itself (GSTR-1 consumes invoice + IRN state produced by T-4A08-01) — owned by [T-4A08-01](./T-4A08-01.md)

## Acceptance criteria

1. **AC-T-4A08-04-1** — GSTR-1 correctness: GIVEN a fixture period with issued invoices, debit notes, and credit notes WHEN the GSTR-1 export generates THEN every outward supply appears exactly once with tax split from the tax engine, and the reconciliation summary reports invoice count = export count with matching tax totals.
2. **AC-T-4A08-04-2** — GSTR-3B correctness: summary tax liability + ITC from inward registers match hand-computed fixture totals; the export follows the pinned portal schema (JSON/CSV fixture validation) with the emitted schema version recorded on the artifact.
3. **AC-T-4A08-04-3** — Reconciliation diagnosability: GIVEN an invoice added after the export's snapshot WHEN reconciliation runs THEN the summary surfaces the count mismatch (invoice count vs export count) rather than silently exporting — the mismatch path is feature-tested.
4. **AC-T-4A08-04-4** — Generation is queued through the finance_reports mechanics (org-scoped artifact, status tracking); export requires `india_statutory:return:export` with step-up (sensitive) and is audited; schema-version bumps ship as adapter releases (version pinned per release, regression fixtures per version).
5. **AC-T-4A08-04-5** — Events `india_statutory.return.generated` (report ref, period, reconciliation summary) and `.failed` (report ref + failure class) are emitted; payloads carry summary counts/totals, never per-invoice amounts.
6. **AC-T-4A08-04-6** — GIVEN a principal lacking `india_statutory:return:view` / `india_statutory:return:export` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A08-04-7** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
