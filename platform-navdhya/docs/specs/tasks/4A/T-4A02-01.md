## Objective

Blanket orders commit a customer to quantities and prices over a validity window on top of the existing order model (no new order aggregate): `sales_blanket_orders` + lines track committed vs released qty, a release creates a standard sales order carrying `blanket_ref` and the blanket line's unit_price, `released_qty` increments atomically under row lock (the inventory §7.3 pattern), over-release rejects, an expiry job flips lapsed blankets, and manual close releases remaining commitment with audit.

## Scope

**In scope:**

- `sales_blanket_orders` (number `BSO-<yyyy>-<seq>`, customer_id, status `open|exhausted|expired|closed`, valid_from/valid_to, currency, totals JSON) + `sales_blanket_order_lines` (variant_id, committed_qty, released_qty, unit_price Money)
- Release flow: creates a standard sales order with `blanket_ref`; order carries the blanket line's unit_price unless overridden with the `sales:order:discount` guard
- Atomic `released_qty` increment in the release transaction (row lock); over-release ⇒ 422 `sales_blanket_over_release`
- Expiry job (`open → expired` past valid_to) + audited manual `:close` releasing remaining commitment
- Endpoints under `/api/v1/sales/blanket-orders` (CRUD, `:release`, `:close`)

**Out of scope:**

- Blanket purchase agreements (supplier-side mirror) — owned by [T-4A03-02](./T-4A03-02.md)
- Price renegotiation mid-term beyond per-release override — owned by By design

## Acceptance criteria

1. **AC-T-4A02-01-1** — Release atomicity holds: GIVEN a blanket line with committed 100 / released 90 WHEN two concurrent releases of 20 race THEN exactly one succeeds and the other receives 422 `sales_blanket_over_release` (row-lock pattern, asserted by concurrency test).
2. **AC-T-4A02-01-2** — Release creates a standard sales order carrying `blanket_ref` and the blanket line's unit_price; a price override without `sales:order:discount` rejects, and with it succeeds (both paths feature-tested).
3. **AC-T-4A02-01-3** — The expiry job flips `open → expired` past `valid_to` without touching released qty; manual `:close` releases the remaining commitment, writes an audit record, and requires step-up (sensitive action).
4. **AC-T-4A02-01-4** — `POST /api/v1/sales/blanket-orders/{id}/lines/{lineId}:release` validates qty > 0 and blanket status `open` — releases against exhausted/expired/closed blankets reject with a named state error; totals JSON is recomputed in the same transaction as `released_qty`.
5. **AC-T-4A02-01-5** — Events `sales.blanket.created` / `.released` / `.expired` / `.closed` are emitted with blanket + line refs; `.released` carries the created order id and the released qty.
6. **AC-T-4A02-01-6** — GIVEN a principal lacking `sales:blanket:view` / `sales:blanket:create` / `sales:blanket:update` / `sales:blanket:close` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A02-01-7** — Tenant isolation holds: every new table (`sales_blanket_orders`, `sales_blanket_order_lines`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A02-01-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
