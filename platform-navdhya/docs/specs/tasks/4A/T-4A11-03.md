## Objective

Recurring postings become template-driven: `gl_recurring_templates` (name, journal_id, frequency `weekly|monthly|quarterly|yearly`, anchor_day, line_template JSON using the posting engine's account-expression template grammar, status, last_run_period) feed a scheduler that generates a DRAFT journal entry per active template per period — idempotent per (template_id, period key) via a unique constraint, so double scheduler runs never double-generate. Generated entries flow through the normal manual-journal approval workflow with SoD (`sod.journal_post_approve`); the engine NEVER auto-posts. Skips (missing account mapping, closed period) land in `posting_errors` + `gl.recurring.skipped`.

## Scope

**In scope:**

- `gl_recurring_templates`: `name`, `journal_id`, `frequency` (`weekly|monthly|quarterly|yearly`), `anchor_day`, `line_template` JSON (account expressions per the posting engine's template grammar), `status`, `last_run_period` NULL
- Scheduler generates a draft journal entry per active template per period — idempotent per (template_id, period key) via unique constraint (double scheduler runs never double-generate)
- Generated entries flow through the normal manual-journal approval workflow (SoD `sod.journal_post_approve`); the engine never auto-posts
- Skips (missing account mapping, closed period) land in `posting_errors` + `gl.recurring.skipped` event
- `execute` = run-now action (`gl:recurring:execute`, sensitive); events `gl.recurring.generated`, `gl.recurring.skipped`

**Out of scope:**

- Auto-posting of recurring entries — prohibited by design (approval + SoD always apply) — owned by By design
- Recurring templates for sub-module postings (expenses, payroll) — owned by Sub-modules own their posting rules

## Acceptance criteria

1. **AC-T-4A11-03-1** — Idempotent generation holds: GIVEN an active monthly template WHEN the scheduler runs twice for the same period (retry/race) THEN exactly one draft journal entry exists for (template_id, period key) — asserted against the unique constraint; `last_run_period` advances once.
2. **AC-T-4A11-03-2** — Never auto-posts: generated entries are drafts that require the normal manual-journal approval workflow with SoD (`sod.journal_post_approve`) — an architecture + feature test asserts no scheduler path can post directly (no posting-engine call outside the approval flow).
3. **AC-T-4A11-03-3** — Period-key correctness: weekly/monthly/quarterly/yearly frequencies with their anchor_day produce the expected period keys (fixture matrix incl. month-end anchoring); a generated draft's lines resolve the template's account expressions against the current chart of accounts.
4. **AC-T-4A11-03-4** — Skip handling: GIVEN a template whose account mapping is missing (or whose period is closed) WHEN the scheduler runs THEN no draft is created, the skip lands in `posting_errors` with a diagnosable reason, and `gl.recurring.skipped` emits (template + period + reason) — the next healthy period generates normally.
5. **AC-T-4A11-03-5** — Events `gl.recurring.generated` (template + draft entry refs) and `gl.recurring.skipped` (template + period + reason) are emitted; payloads carry refs only, never ledger amounts.
6. **AC-T-4A11-03-6** — GIVEN a principal lacking `gl:recurring:view` / `gl:recurring:create` / `gl:recurring:update` / `gl:recurring:execute` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A11-03-7** — Tenant isolation holds: every new table (`gl_recurring_templates`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A11-03-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
