## Objective

Employees raise purchase requisitions that flow through a workflow approval chain with segregation of duties (approver ≠ requester), then convert to PO drafts grouped by suggested supplier — without touching the PO aggregate's core state machine. Conversion is idempotent per requisition, each draft carries `requisition_ref`, and the full lifecycle emits the requisition event family.

## Scope

**In scope:**

- `purchase_requisitions` (number `PR-<yyyy>-<seq>`, requested_by membership_id, org_id, status machine `draft|pending_approval|approved|converted|cancelled`, needed_by, justification, totals JSON) + `purchase_requisition_lines` (variant_id, qty, suggested_supplier_id NULL, notes)
- Approval as a workflow transition (`purchasing:requisition:approve`, sensitive above the tenant amount threshold); approval-chain SoD: approver MUST differ from `requested_by` (approval_chain pattern)
- Conversion: approved lines grouped by suggested supplier → PO **drafts** via the standard PO creation path, each draft carrying `requisition_ref`; idempotent per requisition
- Endpoints under `/api/v1/purchasing/requisitions` (CRUD, `:submit`, `:approve`, `:reject`, `:convert`)
- Events `purchasing.requisition.created` / `.submitted` / `.approved` / `.rejected` / `.converted`

**Out of scope:**

- Requisition budgeting / budget checks — owned by Deferred post-v1
- Direct conversion to non-PO documents — owned by By design

## Acceptance criteria

1. **AC-T-4A03-01-1** — SoD holds on approval: GIVEN a requisition WHERE requested_by = actor WHEN the same actor attempts `:approve` THEN the platform rejects with 403 `sod_conflict` and writes a denial audit record; a different approver with `purchasing:requisition:approve` succeeds.
2. **AC-T-4A03-01-2** — Conversion correctness: GIVEN an approved requisition with lines spanning two suggested suppliers WHEN `:convert` runs THEN exactly two PO drafts are created via the standard PO creation path, each line lands on the draft matching its suggested supplier, and every draft carries `requisition_ref`; lines without a suggested supplier group into a draft flagged for buyer assignment.
3. **AC-T-4A03-01-3** — `POST /api/v1/purchasing/requisitions/{id}:convert` is idempotent per requisition: replaying returns the previously created PO drafts without creating duplicates, and converting a non-approved requisition rejects with a named state error.
4. **AC-T-4A03-01-4** — Approval above the tenant amount threshold escalates to a second approver via the workflow machine; below threshold a single approval transitions the requisition to `approved` (both paths feature-tested).
5. **AC-T-4A03-01-5** — Events `purchasing.requisition.created` / `.submitted` / `.approved` / `.rejected` / `.converted` are emitted with requisition + line refs; `.converted` carries the created PO draft ids; `.rejected` carries the rejection note.
6. **AC-T-4A03-01-6** — GIVEN a principal lacking `purchasing:requisition:view` / `purchasing:requisition:create` / `purchasing:requisition:update` / `purchasing:requisition:approve` / `purchasing:requisition:convert` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A03-01-7** — Tenant isolation holds: every new table (`purchase_requisitions`, `purchase_requisition_lines`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A03-01-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
