## Objective

BOM lines gain `line_kind` (`component|by_product|scrap`, additive, default `component`) with `output_qty_ratio` for non-component kinds. At work-order close, by-product lines are received into stock as receipt movements (`ref_type=work_order_byproduct`) at the tenant's valuation choice (`net_realizable_value|zero`, manufacturing setting); received qty = output qty × ratio with operator adjustment allowed within ±10% (audited). Scrap lines post scrap issue movements plus a balanced GL entry via the posting engine (debit scrap/loss account, credit WIP) using the absorbed cost basis. Events carry quantities + refs — costs stay in the ledger, not events. Postings remain under the existing sensitive `manufacturing:posting:create` permission.

## Scope

**In scope:**

- BOM lines gain `line_kind` (`component|by_product|scrap`, additive, default `component`) + `output_qty_ratio` for non-component kinds; edits under existing `manufacturing:bom:*` permissions
- By-products at work-order close: receipt movements (`ref_type=work_order_byproduct`) into stock at the tenant's valuation choice (`net_realizable_value|zero`, manufacturing setting); received qty = output qty × `output_qty_ratio`
- Operator adjustment of by-product received qty within ±10% (audited); adjustments outside the band reject
- Scrap at close: scrap issue movements + a balanced GL entry via the posting engine (debit scrap/loss account, credit WIP) using the absorbed cost basis
- Events `manufacturing.order.byproduct_received`, `manufacturing.order.scrap_recorded` (quantities + refs; costs stay in the ledger, not events)

**Out of scope:**

- By-product re-use as BOM components (secondary routing) — owned by Deferred post-v1
- Scrap rework recovery flows — owned by Quality/NCR domain

## Acceptance criteria

1. **AC-T-4A10-02-1** — By-product receipt correctness: GIVEN a BOM with a by-product line (`output_qty_ratio` 0.1) and a work order completing 100 output units WHEN the work order closes THEN a receipt movement with `ref_type=work_order_byproduct` receives 10 units into stock; under the `net_realizable_value` setting the receipt carries the configured NRV cost basis, under `zero` it carries zero cost (both modes fixture-tested).
2. **AC-T-4A10-02-2** — Adjustment band: an operator adjusting by-product received qty within ±10% of the ratio-computed qty succeeds with an audit record (old/new qty + reason); an adjustment outside the band rejects with a named 422 error.
3. **AC-T-4A10-02-3** — Scrap posting balance: GIVEN a scrap line WHEN the work order closes THEN a scrap issue movement posts and the posting engine produces a balanced GL entry (debit scrap/loss account, credit WIP) at the absorbed cost basis — the posting engine is consumed, never written around (architecture test asserts no direct ledger writes).
4. **AC-T-4A10-02-4** — `line_kind` defaults to `component` (existing BOMs unaffected — backfill = default); non-component kinds require `output_qty_ratio` > 0 (validation at BOM edit); the work-order close state machine is unchanged (by-product/scrap posting hooks into close, no new states).
5. **AC-T-4A10-02-5** — Events `manufacturing.order.byproduct_received` (work order + variant refs, received qty) and `manufacturing.order.scrap_recorded` (work order + qty) are emitted; payload-schema tests assert no monetary amounts appear (costs stay in the ledger).
6. **AC-T-4A10-02-6** — GIVEN a principal lacking `manufacturing:posting:create` / `manufacturing:bom:update` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A10-02-7** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).

## Risks & notes

- NRV valuation choice is a manufacturing setting — changing it mid-period applies to future closes only (no retroactive re-valuation)
- Scrap GL mapping (scrap/loss account) rides `account_mappings`; unmapped accounts fail the close posting into `posting_errors` rather than posting unbalanced
