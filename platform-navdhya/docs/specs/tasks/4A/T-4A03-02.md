## Objective

Blanket purchase agreements mirror sales blanket orders against suppliers: `purchase_blanket_orders` + lines track committed vs released qty at an agreed unit_cost over a validity window. Releases create PO drafts carrying `blanket_ref` with the same row-locked atomic increment and over-release block as the sales pattern (T-4A02-01); released POs then follow the normal PO approval workflow.

## Scope

**In scope:**

- `purchase_blanket_orders` (number `BPO-<yyyy>-<seq>`, supplier_id, status `open|exhausted|expired|closed`, valid_from/valid_to, currency, totals JSON) + `purchase_blanket_order_lines` (variant_id, committed_qty, released_qty, unit_cost Money)
- Release creates PO **drafts** with `blanket_ref` at the blanket line's unit_cost; atomic `released_qty` increment under row lock (sales §3.2 pattern); over-release blocked
- Approval of released POs follows the normal PO workflow (no blanket-specific state machine beyond open/exhausted/expired/closed)
- Expiry job (`open → expired` past valid_to) + audited manual `:close`
- Events `purchasing.blanket.created` / `.released` / `.expired` / `.closed`. Permissions: `purchasing:blanket:view|create|update|close` (close sensitive)

**Out of scope:**

- Supplier negotiation / RFQ flows — owned by Deferred post-v1
- Release directly to an approved PO (releases always draft first) — owned by By design

## Acceptance criteria

1. **AC-T-4A03-02-1** — Release atomicity holds (mirroring T-4A02-01): GIVEN a blanket line with committed 100 / released 90 WHEN two concurrent releases of 20 race THEN exactly one succeeds; the other is blocked; over-release attempts reject with a named 422 error.
2. **AC-T-4A03-02-2** — Release creates a PO draft carrying `blanket_ref` and the blanket line's unit_cost; the draft enters the normal PO approval workflow (approval transitions are unchanged from baseline PO behavior).
3. **AC-T-4A03-02-3** — The expiry job flips `open → expired` past `valid_to` without touching released qty; manual `:close` releases remaining commitment, requires step-up (sensitive), and writes an audit record.
4. **AC-T-4A03-02-4** — `POST /api/v1/purchasing/blanket-orders/{id}/lines/{lineId}:release` validates qty > 0 and blanket status `open`; releases against exhausted/expired/closed blankets reject with a named state error; totals JSON recomputes in the same transaction as `released_qty`.
5. **AC-T-4A03-02-5** — Events `purchasing.blanket.created` / `.released` / `.expired` / `.closed` are emitted with blanket + line refs; `.released` carries the created PO draft id and released qty.
6. **AC-T-4A03-02-6** — GIVEN a principal lacking `purchasing:blanket:view` / `purchasing:blanket:create` / `purchasing:blanket:update` / `purchasing:blanket:close` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A03-02-7** — Tenant isolation holds: every new table (`purchase_blanket_orders`, `purchase_blanket_order_lines`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A03-02-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
