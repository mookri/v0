## Objective

One row per physical unit: `stock_serials` (serial_number UQ per tenant+variant, status machine `in_stock|reserved|issued|returned|scrapped`, current_location_id, received/issued refs) + append-only `stock_serial_history` trace. Serials are captured at GRN (per-unit entry or file import), transfer, and issue; any movement of a serial-tracked variant MUST name its serials — qty vs serial-count mismatch rejects with 422 `inventory_serial_count_mismatch`. Reservation reserves specific serials (additive `stock_reservations.serial_ids`); fulfillment issues exactly those serials (substitution requires explicit operator action + audit). Service and warranties consume serial state via the published `SerialQuery` contract — never by reading inventory tables.

## Scope

**In scope:**

- `stock_serials` (variant_id, serial_number UQ per tenant+variant, status `in_stock|reserved|issued|returned|scrapped`, current_location_id NULL, received_ref, issued_ref NULL) + `stock_serial_history` (serial_id, movement_id, occurred_at; append-only)
- Serial capture at GRN (per-unit entry or file import), transfer, and issue; movement of a serial-tracked variant MUST name its serials — mismatch ⇒ 422 `inventory_serial_count_mismatch`
- Serial-specific reservation: additive `stock_reservations.serial_ids`; fulfillment issues the reserved serials; substitution requires explicit operator action + audit record
- `SerialQuery` contract published for service (tickets) + warranties (contracts §10.3) — serial state consumed via contract only
- Serial lifecycle events carried on existing movement events (additive serial refs); no new event family

**Out of scope:**

- Directed serial put-away / full WMS slotting — owned by Deferred post-v1 (deferral seam: rows carry location)
- Serial-number printing/label design — owned by Experience phase

## Acceptance criteria

1. **AC-T-4A07-01-1** — Count-mismatch guard: GIVEN a movement of a serial-tracked variant with qty 5 naming 4 serials WHEN the movement is submitted THEN the request rejects with 422 `inventory_serial_count_mismatch`; naming exactly 5 serials succeeds and writes 5 history rows (append-only).
2. **AC-T-4A07-01-2** — Reserved-serial issuance: GIVEN a reservation holding serial_ids [S1,S2] WHEN fulfillment issues THEN exactly S1,S2 leave stock (`issued` + issued_ref set); a substitution attempt without the explicit operator action rejects, and with it writes an audit record naming old + new serials.
3. **AC-T-4A07-01-3** — Serial uniqueness + status machine: serial_number is UQ per (tenant, variant); status transitions follow `in_stock → reserved → issued` (+ `returned`/`scrapped` paths via the standard return/adjustment flows) — illegal transitions reject with a named state error.
4. **AC-T-4A07-01-4** — `SerialQuery` contract isolation: the contract serves status/location/history scoped to the caller's tenant — a cross-tenant serial lookup returns no rows (contract test), and the architecture test asserts service + contracts modules never query `stock_serials` directly.
5. **AC-T-4A07-01-5** — Movement events for serial-tracked variants carry additive serial refs (serial ids + status transitions); the history trace is append-only — a schema test asserts no UPDATE/DELETE path exists on `stock_serial_history`.
6. **AC-T-4A07-01-6** — GIVEN a principal lacking `inventory:stock:view` / `inventory:transfer:create` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A07-01-7** — Tenant isolation holds: every new table (`stock_serials`, `stock_serial_history`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A07-01-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
