## Objective

Warranties are contracts with `kind=warranty` linking `serial_ref` to the inventory serial ledger (T-4A07-01). The module publishes the `ContractCoverageQuery` contract: given (serial or customer, date) it resolves the covering contract + remaining terms — consumed by service tickets and POS within effective authority. A coverage probe endpoint (`GET /contracts/coverage?serial=&customer=&date=`) serves both humans and the contract implementation. Claim events (`contracts.warranty.claimed`) carry the ticket ref only — no PII. Serial state is consumed via inventory's `SerialQuery` contract, never by direct table reads.

## Scope

**In scope:**

- `kind=warranty` contracts link `serial_ref` to the inventory serial ledger (consumes `SerialQuery`, T-4A07-01); warranty terms ride on `contract_lines.coverage` JSON
- `ContractCoverageQuery` contract published: (serial or customer, date) → covering contract + remaining terms; consumed by service tickets + POS within effective authority
- Coverage probe endpoint `GET /api/v1/contracts/coverage?serial=&customer=&date=` under `contracts:contract:view` (also the contract's HTTP implementation)
- Claim event `contracts.warranty.claimed` (ticket ref — no PII) emitted when a service ticket invokes coverage

**Out of scope:**

- Contract lifecycle + renewal machinery (shared tables) — owned by [T-4A09-01](./T-4A09-01.md)
- Repair/claim fulfillment workflows inside service — owned by Service baseline
- Warranty registration portals (end-customer self-service) — owned by Deferred post-v1

## Acceptance criteria

1. **AC-T-4A09-02-1** — Coverage probe correctness: GIVEN a warranty contract covering serial S from 2026-01-01 to 2027-01-01 WHEN coverage is probed for (S, 2026-06-15) THEN the covering contract + remaining terms return; probing (S, 2027-02-01) returns no coverage (out-of-window); a customer-level probe returns covering service contracts for that customer's date (fixture matrix).
2. **AC-T-4A09-02-2** — Serial linkage: a warranty's `serial_ref` must resolve via `SerialQuery` — creating a warranty against an unknown/other-tenant serial rejects; the architecture test asserts the contracts module never queries `stock_serials` directly.
3. **AC-T-4A09-02-3** — Service consumption: GIVEN a service ticket on serial S WHEN the service module resolves coverage through `ContractCoverageQuery` THEN the ticket receives the covering contract + remaining terms, and `contracts.warranty.claimed` emits with the ticket ref only (payload-schema test asserts no PII).
4. **AC-T-4A09-02-4** — The coverage probe endpoint answers within effective authority: a principal without `contracts:contract:view` receives 403; cross-tenant serial/customer probes return no coverage rather than leaking existence (contract + isolation tests).
5. **AC-T-4A09-02-5** — `contracts.warranty.claimed` is emitted exactly once per coverage invocation that finds a covering contract (no event for no-coverage probes); the event carries ticket ref + contract id, never customer personal data.
6. **AC-T-4A09-02-6** — GIVEN a principal lacking `contracts:contract:view` / `contracts:warranty:view` / `contracts:warranty:configure` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A09-02-7** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
