## Objective

Reports push themselves: `report_schedules` bind a report_ref (finance_reports definition or analytics KPI ref) to recipients (membership ids), frequency (`daily|weekly|monthly`, anchor_day), format (`pdf|xlsx|csv`), and filters. The scheduler generates the artifact through the owning report's queued path, then dispatches via notifications with a tenant-scoped signed file URL (kernel Files); delivery is logged in `notifications_log` with campaign tag `scheduled_report`. Org-scoped fan-out is normative: the report executes once per distinct recipient org-scope set — a recipient never receives rows beyond their org visibility. Schedule creation requires the underlying report's view permission, and recipients are validated to hold it too (422 `report_schedule_recipient_unauthorized` otherwise).

## Scope

**In scope:**

- `report_schedules`: `report_ref` (finance_reports definition or analytics KPI ref), `recipients` JSON (membership ids), `frequency` (`daily|weekly|monthly`), `anchor_day` NULL, `format` (`pdf|xlsx|csv`), `filters` JSON, `status`, `last_sent_at` NULL
- Scheduler generates the artifact through the owning report's queued path (finance_reports mechanics), then dispatches via notifications with a tenant-scoped signed file URL (kernel Files); delivery logged in `notifications_log` with campaign tag `scheduled_report`
- **Org-scoped fan-out (normative)**: the report executes once per distinct recipient org-scope set — a recipient never receives rows beyond their org visibility; architecture test: a crafted schedule with mixed-scope recipients produces per-scope artifacts
- Authorization: schedule creation requires the underlying report's view permission; recipients are validated to hold it too (422 `report_schedule_recipient_unauthorized` otherwise)
- Events `finance_reports.schedule.sent` / `.failed`

**Out of scope:**

- Real-time alerting beyond scheduled dispatch (threshold events such as `finance_reports.margin.below_threshold` belong to their owning modules + notifications) — owned by By design
- Report definition authoring (finance_reports owns definitions; schedules only reference them) — owned by Finance reports baseline

## Acceptance criteria

1. **AC-T-4A12-01-1** — Org-scoped fan-out holds (normative): GIVEN a schedule whose recipients span two distinct org-scope sets WHEN dispatch executes THEN the report runs once per scope set producing per-scope artifacts, and each recipient receives only rows within their org visibility — the architecture test crafts a mixed-scope schedule and asserts per-scope artifacts (no cross-scope row leakage).
2. **AC-T-4A12-01-2** — Recipient authorization: GIVEN a recipient lacking the underlying report's view permission WHEN the schedule is created/updated to include them THEN the request rejects with 422 `report_schedule_recipient_unauthorized`; schedule creation by a principal without the report's view permission also rejects (both paths feature-tested).
3. **AC-T-4A12-01-3** — Dispatch flow: the scheduler generates the artifact through the owning report's queued path, dispatches via notifications with a tenant-scoped signed file URL (kernel Files), logs delivery in `notifications_log` with campaign tag `scheduled_report`, and advances `last_sent_at` — artifact generation failures land in `.failed` without partial sends.
4. **AC-T-4A12-01-4** — Cadence correctness: `daily|weekly|monthly` frequencies with their `anchor_day` produce dispatches on the expected schedule (cadence matrix fixtures incl. month-end anchoring); disabled schedules (`status`) are skipped entirely; format selection (`pdf|xlsx|csv`) governs the generated artifact.
5. **AC-T-4A12-01-5** — Events `finance_reports.schedule.sent` (schedule ref, scope-set count, recipient count) and `finance_reports.schedule.failed` (schedule ref + failure class) are emitted; payloads carry refs + counts, never report data.
6. **AC-T-4A12-01-6** — GIVEN a principal lacking `finance_reports:schedule:view` / `finance_reports:schedule:create` / `finance_reports:schedule:update` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A12-01-7** — Tenant isolation holds: every new table (`report_schedules`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A12-01-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
