## Objective

Invoicing gains a `kind` discriminator (`invoice|pro_forma`, additive, default `invoice`) so pro-forma documents compose exactly like invoices (lines, totals, tax) but are excluded from AR and GL posting by a posting-rule filter on `kind=invoice`. A one-way, idempotent `:convert` promotes a pro-forma into a real invoice (copies lines, assigns the invoice number from the numbering scheme, emits the conversion event) under the existing issue guard — no new permissions.

## Scope

**In scope:**

- Additive `kind` column (`invoice|pro_forma`, default `invoice`) on the invoice aggregate + model guards
- Posting-rule filter: AR + GL posting applies to `kind=invoice` only (pro-forma never posts)
- `POST /invoices/{id}:convert` (`invoicing:invoice:issue` guard) — copies lines, assigns invoice number from the scheme, idempotent + one-way
- Events `invoicing.proforma.issued` / `.converted`

**Out of scope:**

- Pro-forma as a sales-document type owned by the sales module — invoicing owns it because it shares numbering + posting-filter rules — owned by By design
- Partial conversion (convert a subset of lines) — owned by By design — conversion is whole-document

## Acceptance criteria

1. **AC-T-4A02-03-1** — Posting exclusion holds: GIVEN a pro-forma invoice WHEN the posting engine runs THEN no AR or GL posting is produced (posting rules filter `kind=invoice` only), while a real invoice of identical composition posts normally.
2. **AC-T-4A02-03-2** — `POST /invoices/{id}:convert` is idempotent and one-way: the first call copies lines, assigns the invoice number from the numbering scheme, and emits `invoicing.proforma.converted`; replaying returns the stored result without creating a second invoice; converting an already-converted document is a no-op returning the existing invoice.
3. **AC-T-4A02-03-3** — Conversion requires the `invoicing:invoice:issue` guard; a pro-forma converts to a real invoice that then flows through standard invoice issuance (events, numbering) with no pro-forma residue.
4. **AC-T-4A02-03-4** — The `kind` column is additive with default `invoice`; existing invoices are unaffected (backfill = default), and the model rejects any `kind` outside the two-value enum.
5. **AC-T-4A02-03-5** — Events `invoicing.proforma.issued` (on pro-forma creation) and `invoicing.proforma.converted` (carrying source pro-forma id + resulting invoice id) are emitted; no new permissions are introduced.
6. **AC-T-4A02-03-6** — GIVEN a principal lacking `invoicing:invoice:issue` / `invoicing:invoice:view` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A02-03-7** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
