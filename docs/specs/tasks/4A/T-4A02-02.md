## Objective

Backorders become first-class: a listener-built `sales_backorder_snapshots` table surfaces confirmed order lines with `reserved_qty < qty` (fed by `inventory.reservation.partial_flagged` payloads joined locally within sales), a report endpoint exposes them, and `POST /api/v1/sales/backorders:allocate` consumes available stock FIFO by order confirmation time — idempotent per run_id, with per-line outcomes and standard reservation events. Stock receipts auto-trigger debounced allocation runs for variants with pending backorders.

## Scope

**In scope:**

- `sales_backorder_snapshots` (listener-refreshed from `inventory.reservation.partial_flagged` + local sales joins — no cross-module joins)
- Backorder report endpoint `GET /api/v1/sales/backorders` (`sales:backorder:view`)
- `POST /api/v1/sales/backorders:allocate` (`sales:backorder:allocate`) — FIFO by order confirmation time; idempotent per (run_id); per-line outcome report
- Automatic trigger: `inventory.stock.received` for a variant with pending backorders enqueues a debounced allocation run
- Events `sales.backorder.flagged` / `.allocated` / `.allocation_run_completed`

**Out of scope:**

- Purchase-triggered replenishment suggestions (supply-chain consumes allocation events) — owned by P4 supply-chain baseline
- Partial-allocation UI workflows beyond the outcome report — owned by Experience phase

## Acceptance criteria

1. **AC-T-4A02-02-1** — FIFO allocation order holds: GIVEN three confirmed backorders confirmed at t1 < t2 < t3 and stock covering exactly two WHEN an allocation run executes THEN the t1 and t2 lines are allocated in confirmation order, t3 remains backordered, and the run result reports per-line outcomes.
2. **AC-T-4A02-02-2** — `POST /api/v1/sales/backorders:allocate` is idempotent per (run_id): replaying the same run_id returns the stored outcome without re-allocating stock or re-emitting allocation events.
3. **AC-T-4A02-02-3** — Automatic trigger: publishing `inventory.stock.received` for a variant with pending backorders enqueues a debounced allocation run that consumes only that variant's available stock and emits `sales.backorder.allocated` per satisfied line.
4. **AC-T-4A02-02-4** — `sales_backorder_snapshots` is built exclusively from `inventory.reservation.partial_flagged` payloads + local sales tables — the architecture test asserts the listener performs no cross-module joins.
5. **AC-T-4A02-02-5** — Events `sales.backorder.flagged` / `.allocated` / `.allocation_run_completed` are emitted; `.allocation_run_completed` carries run_id + allocated/skipped counts; successful allocations also emit the standard reservation events.
6. **AC-T-4A02-02-6** — GIVEN a principal lacking `sales:backorder:view` / `sales:backorder:allocate` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A02-02-7** — Tenant isolation holds: every new table (`sales_backorder_snapshots`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A02-02-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
