## Objective

Collections automation on AR aging: `ar_dunning_levels` (tenant config: level number, days-past-due threshold, notice template, optional fee, channel) drive runs (`ar_dunning_runs`) that scan overdue open invoices — excluding invoices with active disputes or payment-in-flight (payments contract) — and select each customer's next level (max prior level + 1, capped). Notices (`ar_dunning_notices`) are sent via notifications (email with statement PDF through kernel Files); optional level fees post via the posting engine (debit AR dunning-fee receivable, credit fee income), idempotent per (invoice, level). Runs are scheduled or manual (`ar:dunning:execute`, sensitive).

## Scope

**In scope:**

- `ar_dunning_levels` (tenant config): level number, days-past-due threshold, notice template, fee (Money) NULL, channel. `ar_dunning_runs`: run_date, status. `ar_dunning_notices`: customer_id, level, invoice refs JSON, amount_due (Money), sent_at, run_id
- Run (scheduled or manual): scans AR aging for overdue open invoices; excludes invoices with active disputes or payment-in-flight (payments contract); selects the customer's next level (max prior level + 1, capped)
- Notices sent via notifications (email with statement PDF, kernel Files); delivery tracked on the notice row
- Optional level fee posts via the posting engine (debit AR dunning-fee receivable, credit fee income) — fee posting idempotent per (invoice, level)
- Events `ar.dunning.run_completed`, `ar.dunning.notice_sent`, `ar.dunning.fee_charged`. Permissions: `ar:dunning:view|execute|configure` (execute + configure sensitive)

**Out of scope:**

- Legal escalation / collections agency handoff — owned by Deferred post-v1
- Payment-plan negotiation workflows — owned by By design

## Acceptance criteria

1. **AC-T-4A11-04-1** — Level progression holds: GIVEN a customer at dunning level 2 WHEN the run executes THEN the notice goes out at level 3 (max prior + 1); a customer already at the configured cap stays at the cap (no level overflow); a fresh overdue customer starts at level 1 — progression matrix feature-tested.
2. **AC-T-4A11-04-2** — Exclusion correctness: invoices with active disputes or payment-in-flight (per the payments contract) are excluded from the run's notice set — exclusion fixtures assert neither appears on any notice while disputed/in-flight, and both re-enter the run after resolution.
3. **AC-T-4A11-04-3** — Fee posting idempotency: GIVEN a level with a configured fee WHEN notices issue THEN the fee posts via the posting engine (debit AR dunning-fee receivable, credit fee income, balanced); a re-run or retry for the same (invoice, level) never posts a second fee (idempotency asserted by replay test).
4. **AC-T-4A11-04-4** — Notice delivery: notices send via notifications with a statement PDF (kernel Files artifact); the notice row records customer, level, invoice refs, amount_due, run_id, and sent_at; `ar.dunning.notice_sent` emits per notice and `ar.dunning.run_completed` emits once per run with counts.
5. **AC-T-4A11-04-5** — Events `ar.dunning.run_completed` (run ref + counts), `ar.dunning.notice_sent` (notice ref), `ar.dunning.fee_charged` (invoice + level refs) are emitted; fee amounts stay in the ledger — event payloads carry refs, levels, and counts only.
6. **AC-T-4A11-04-6** — GIVEN a principal lacking `ar:dunning:view` / `ar:dunning:execute` / `ar:dunning:configure` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A11-04-7** — Tenant isolation holds: every new table (`ar_dunning_levels`, `ar_dunning_runs`, `ar_dunning_notices`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A11-04-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
