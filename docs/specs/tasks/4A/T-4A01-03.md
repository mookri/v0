## Objective

The platform gains its polymorphic collaboration timeline: `crm_activities` (call/meeting/task/note/email) attach to any registered subject type (leads, opportunities, customers, tickets, projects) with kernel-validated subject registry, append+complete semantics, and reads inheriting the subject's view permission. Campaigns carry attribution (leads → opportunities → orders via `source=crm`), and opportunities bind customer contacts with deal roles.

## Scope

**In scope:**

- `crm_activities` polymorphic timeline + subject-type registry validation; append+complete rules (no edits after completion)
- `crm_campaigns` + campaign attribution snapshot on conversion; quotes/orders from converted opportunities carry `source=crm` + `source_ref`
- `crm_opportunity_contacts` with roles (decision_maker|influencer|buyer|user|coach) + primary flag
- Activity/campaign endpoints under `/api/v1/crm`; `crm.activity.logged` event feeding customer 360 + analytics

**Out of scope:**

- Campaign effectiveness computation (analytics consumes events) — owned by P6 analytics
- Email synchronization with external mailboxes — owned by Deferred post-v1

## Acceptance criteria

1. **AC-T-4A01-03-1** — Timeline security holds: activity reads inherit the subject resource's view permission — GIVEN an actor without `service:ticket:view` WHEN reading a ticket's timeline THEN the ticket's activities are not returned (no leakage via the timeline).
2. **AC-T-4A01-03-2** — Activities are append + complete only: completed activities reject edits; corrections create a new activity referencing the old id (asserted by model guard + feature test).
3. **AC-T-4A01-03-3** — Attribution chain holds: a lead converted with campaign_id snapshots attribution onto the opportunity, and quotes/orders created from that opportunity carry `source=crm` + `source_ref=<opportunity_id>` (chain asserted end-to-end in the feature suite).
4. **AC-T-4A01-03-4** — Opportunity contacts are unique per (opportunity, contact) with one primary; subject types on activities validate against the kernel registry of module codes (unknown subject types reject).
5. **AC-T-4A01-03-5** — Events `crm.activity.logged` (subject ref, kind, actor), `crm.campaign.created` / `.updated` are emitted; every activity write produces the logged event.
6. **AC-T-4A01-03-6** — GIVEN a principal lacking `crm:activity:view` / `crm:activity:create` / `crm:campaign:view` / `crm:campaign:create` / `crm:opportunity:update` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A01-03-7** — Tenant isolation holds: every new table (`crm_activities`, `crm_campaigns`, `crm_opportunity_contacts`) is covered by the `AssertTenantIsolation` matrix — cross-tenant reads return no rows and unresolvable tenant contexts fail closed (enforced by the [Tenant Isolation Suite (standing)](../../../19-testing/testing-strategy.md#tenant-isolation-suite-standing)).
8. **AC-T-4A01-03-8** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
