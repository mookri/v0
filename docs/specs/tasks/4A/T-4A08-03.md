## Objective

Payroll run lines gain statutory components computed by the India statutory adapter (never inside the jurisdiction-generic payroll engine): PF (employee + employer shares per wage-ceiling config), ESI (wage-basis eligibility), and Professional Tax (state-wise slab tables in adapter config). Computation is deterministic per payroll determinism — same inputs ⇒ byte-identical statutory lines; slab tables are versioned, effective-dated config. Filing inputs are monthly export artifacts (ECR for PF, ESI contribution file) generated through kernel Files — filing itself (portal upload) stays out-of-platform in v1. Events carry run refs only, never amounts (payroll sensitivity class).

## Scope

**In scope:**

- Statutory payroll components computed by the adapter: PF (employee + employer shares per wage-ceiling config), ESI (wage-basis eligibility), Professional Tax (state-wise slab tables in adapter config)
- Determinism guarantee: same inputs ⇒ byte-identical statutory lines (payroll determinism applies); slab tables are versioned config, effective-dated, and the version used is recorded per run
- Filing inputs: monthly export files — ECR (PF) + ESI contribution file — generated as report artifacts via kernel Files; portal filing stays out-of-platform in v1
- Events `india_statutory.payroll.components_computed` (run ref only — no amounts in events)

**Out of scope:**

- Portal filing / upload automation — owned by Out-of-platform in v1 (tenant uploads the artifacts)
- Statutory challans / payment scheduling — owned by Deferred post-v1
- Any statutory logic inside the payroll engine — prohibited by ADR-0008 — owned by By design

## Acceptance criteria

1. **AC-T-4A08-03-1** — Determinism holds: GIVEN identical payroll inputs and slab-config version WHEN the adapter computes twice THEN both runs produce byte-identical statutory lines (PF employee/employer shares, ESI, PT) — asserted by determinism fixtures; slab-version changes apply only per effective date.
2. **AC-T-4A08-03-2** — Engine separation: the payroll engine remains jurisdiction-generic — the architecture test asserts statutory computation lives only in the india_statutory adapter (no India-specific branches in payroll code); run lines carry statutory components as additive slots.
3. **AC-T-4A08-03-3** — Slab correctness: PT computes against the employee's state slab table (state-wise config), PF respects the wage ceiling config (employee + employer shares), and ESI applies only to wage-eligible employees — boundary fixtures at slab edges pass.
4. **AC-T-4A08-03-4** — Filing exports: monthly ECR (PF) and ESI contribution files generate as kernel-Files artifacts in the portal formats (fixture-validated); exports require `india_statutory:filing:export` with step-up (sensitive) and are audited; the artifact records the slab-config + schema versions used.
5. **AC-T-4A08-03-5** — Event `india_statutory.payroll.components_computed` carries the payroll run ref only — a payload-schema test asserts no monetary amounts or employee identifiers appear in the event (payroll sensitivity class).
6. **AC-T-4A08-03-6** — GIVEN a principal lacking `india_statutory:statutory:view` / `india_statutory:statutory:configure` / `india_statutory:filing:export` WHEN the corresponding request is issued THEN the platform returns 403 with envelope code `authorization_denied` and writes a denial audit record (negative path).
7. **AC-T-4A08-03-7** — The module manifest declares every permission, event, and navigation entry introduced by this task; `platform:sync-permissions` and `module:list` reflect them, and every state change introduced writes an audit record (DoD items 3 + 5).
