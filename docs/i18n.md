# i18n — Navdhya

Scaffolding for multi-language support. Launch-locale: **English** (default,
URL-less). Second locale at launch: **Hindi** (`/hi/...`). The scaffold
(PR 0.55) ships the config, helpers, messages, and a translation pipeline.
URL routing for `/hi/` is wired in **PR 14a (Hindi content)**.

## Locale codes

| Locale | URL prefix | Native name | BCP 47 | Status |
|---|---|---|---|---|
| `en` | _(none)_ | English | `en-IN` | Production |
| `hi` | `/hi` | हिन्दी | `hi-IN` | Scaffolded |

## Adding a translatable string

1. Add the key to `messages/en.json` (the source of truth).
2. Mirror the same key path in `messages/hi.json` (initially copy the
   English value as a placeholder; the pipeline will overwrite it).
3. Run `npm run i18n:check` to confirm the bundles are structurally aligned.
4. Run `npm run i18n:translate -- --to hi` to fill the missing values.

```bash
# Translate every missing key in messages/hi.json
npm run i18n:translate -- --to hi

# Dry run (no writes)
npm run i18n:translate -- --to hi --dry-run

# Translate a single key (useful for quick fixes)
npm run i18n:translate -- --to hi --key "common.learnMore"

# Use the Claude provider instead of DeepL
ANTHROPIC_API_KEY=sk-ant-... npm run i18n:translate -- --to hi --provider claude
```

## Adding a new locale

1. Add the code to `LOCALES` in `i18n.ts`.
2. Add a label entry to `LOCALE_LABELS` and a `HREFLANG_BY_LOCALE` value.
3. Add a `formatCurrency` default in `lib/i18n/formatters.ts` if the
   locale uses a non-INR currency.
4. Create `messages/<locale>.json` (copy `messages/en.json` to start).
5. Run `npm run i18n:translate -- --to <locale>` to translate.
6. Wire the URL prefix in `app/(seo)/[...slug]/page.tsx` (PR 14a).
7. Add the locale to `lib/seo/robots.ts` allowlist if it should be
   crawlable (default: yes).

## URL routing

The scaffold exports two helpers that components will use:

```ts
import { resolveLocaleFromPath, stripLocalePrefix, localizePath } from "@/lib/i18n/locale";

// 1. Detect locale from a request pathname
const locale = resolveLocaleFromPath("/hi/pujas/foo"); // -> "hi"

// 2. Strip the prefix before calling existing SEO/page loaders
const canonical = stripLocalePrefix("/hi/pujas/foo"); // -> "/pujas/foo"

// 3. Build a locale-prefixed href for <Link>
const href = localizePath("/pujas/foo", "hi"); // -> "/hi/pujas/foo"
```

The `inLanguage` alternates JSON-LD (already wired in PR 0.5 AEO) uses
`HREFLANG_BY_LOCALE` for the `hreflang` attribute.

## Server-side message loading

```ts
import { loadMessages, get, getWithFallback } from "@/lib/i18n/messages";

const bundle = await loadMessages("hi");
const title = get(bundle, "home.hero.title"); // -> "प्रामाणिक हिंदू अनुष्ठान, ..."
```

Components can call these directly. The message loader is server-only and
caches per worker process. Cache invalidates on worker restart — for hot
edits during dev, restart `next dev`.

## Formatters

`lib/i18n/formatters.ts` exposes locale-aware `Intl.*` wrappers:

- `formatCurrency(amount, locale, opts?)` — default INR
- `formatNumber(value, locale)` — Indian grouping
- `formatDate(date, locale, opts?)`
- `formatRelative(date, locale, base?)` — `Intl.RelativeTimeFormat`
- `formatList(items, locale)` — `Intl.ListFormat`

## Translation pipeline

Two providers, selected by env var:

- `DEEPL_API_KEY` → `lib/i18n/translate.ts#deeplClient`
- `ANTHROPIC_API_KEY` → `lib/i18n/translate.ts#claudeClient`

When neither is set, both clients **passthrough** the source text. This
means `npm run i18n:translate -- --dry-run` is safe to run anywhere.

The pipeline itself (`scripts/translate.ts`) is plain Node/TSX — no
workflow engine. CI uses it in PR 14a to auto-refresh `messages/hi.json`
whenever `messages/en.json` changes.
